# البناء والإصدار التلقائي

يبدأ workflow ‏`Windows CI and automatic release` تلقائيًا عند كل دفع إلى أي فرع، وكذلك عند فتح طلب دمج إلى `main`. لا يلزم تشغيل اختبارات الفروع يدويًا.

## ما الذي يحدث؟

تُجرى اختبارات JavaScript والبناء، ثم اختبارات Rust وبناء Windows، ثم smoke تفاعلي يتحقق من هندسة الجزيرة والنقرات وعدم القص. تستخدم الفروع وطلبات الدمج رقم patch المرشح التالي لبناء النسخة واختبارها، لكنها لا تكتب رقمًا في المستودع ولا تنشئ إصدارًا. على `main` فقط، وبعد نجاح جميع الفحوص، يثبت workflow رقم patch التالي داخل `0.7.x`، وينشئ مثبّت Windows ويمرر فحوص SHA-256، ثم يحفظ الإصدار كمسودة GitHub للمراجعة.

**لا يحول workflow المسودة إلى إصدار عام ولا يغيّر أحدث إصدار تلقائيًا.** النشر العام يحتاج موافقة صريحة بعد مراجعة رقم الإصدار ورقم البناء والمثبّت وملاحظات الإصدار.

## زيادة رقم الإصدار

السلسلة مقيدة عمدًا إلى `0.7.x`: يحسب workflow patch التالي اعتمادًا على أعلى رقم بين ملفات المشروع ووسوم `tarteel-v0.7.N` الموجودة. قبل بناء المثبّت يزامن الرقم في `package.json` و`package-lock.json` و`src-tauri/Cargo.toml` و`src-tauri/tauri.conf.json`. على `main` يثبت التغيير تلقائيًا في commit إصدار. رقم تشغيل GitHub (`run_number`) هو رقم البناء المتزايد الظاهر في سجل التشغيل وفي بيانات المسودة. توجد اختبارات تمنع الخروج عن `0.7.x` أو اختلاف ملفات النسخ.

## الأمان ومنع التكرار

كل Actions مثبتة على commit SHA ثابت. تشغيلات `main` متسلسلة؛ إذا وصل تحديث أحدث أثناء بناء قديم، لا يحضّر التشغيل القديم إصدارًا. commit ترقية الإصدار الآلي يستخدم `[skip ci]` لمنع دورة تشغيل جديدة. ويمكن لرسالة دمج تهيئة النظام أن تحتوي `[skip release]`: يظل CI يعمل، لكن لا ينشئ مسودة إصدار لمجرد تركيب الأتمتة.
