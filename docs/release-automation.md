# البناء والنشر التلقائي

يبدأ workflow ‏`Windows CI and automatic release` تلقائيًا عند كل دفع إلى أي فرع، وكذلك عند فتح طلب دمج إلى `main`. تُبنى التغييرات وتُختبر دون حاجة إلى تشغيل يدوي.

## ما الذي يحدث؟

تُجرى اختبارات JavaScript وRust، ثم بناء Windows وsmoke تفاعلي يتحقق من هندسة الجزيرة والنقرات وعدم القص. تستخدم الفروع وطلبات الدمج رقم patch المرشح التالي للبناء والاختبار فقط، ولا تكتب رقمًا في المستودع ولا تنشئ إصدارًا.

على `main`، وبعد نجاح كل الاختبارات وWindows smoke، يثبت workflow رقم patch التالي في ملفات المشروع، وينشئ مثبّت Windows، ويتحقق من بصمة SHA-256، ثم ينشئ tag وينشر إصدار GitHub للعامة تلقائيًا مع المثبّت وملاحظات الإصدار وبيانات البناء. لذلك لا يُنشر أي إصدار من فرع أو طلب دمج.

## زيادة رقم الإصدار

السلسلة مقيدة عمدًا إلى `0.7.x`: يحسب workflow patch التالي اعتمادًا على أعلى رقم بين ملفات المشروع ووسوم `tarteel-v0.7.N` الموجودة. يزامن الرقم في `package.json` و`package-lock.json` و`src-tauri/Cargo.toml` و`src-tauri/tauri.conf.json`. على `main`، يثبت التغيير تلقائيًا في commit إصدار. رقم تشغيل GitHub (`run_number`) ورقم الالتزام وبصمة المثبّت تضاف إلى بيانات الإصدار المنشور. توجد اختبارات تمنع الخروج عن `0.7.x` أو اختلاف ملفات النسخ.

## الأمان ومنع التكرار

كل Actions مثبتة على commit SHA ثابت. تشغيلات `main` متسلسلة؛ إذا وصل تحديث أحدث أثناء بناء قديم، لا ينشر التشغيل القديم إصدارًا. لا يبدأ النشر إلا بعد نجاح `version` و`test` و`windows`، ويتحقق أخيرًا من أن tag والإصدار والمثبّت يطابقون الالتزام وبصمة Windows. يستخدم commit ترقية الإصدار الآلي `[skip ci]` لمنع دورة تشغيل جديدة. ويمكن لرسالة commit إعداد سياسة النشر أن تحتوي `[skip release]` كي يجري CI دون إنشاء إصدار منفصل لمجرد تثبيت الأتمتة.
